# 后续改进方向

定位：依托 DeepSeek Harness 的多模型并排讨论与总结插件。优先复用宿主的模型调用、凭证和插件安装机制。以下是可选路径，不是已实现功能；每次选择一个小目标，验收后再扩展。

## 建议顺序

| 优先级 | 值得做的改进 | 可行设计 | 验收标准 |
|---|---|---|---|
| P0：别人能用 | 不同电脑、官方 API 和宿主版本的安装验证 | 从一位真实使用者开始；记录 OS、Harness 版本、profile 和渠道，修复可复现的安装障碍；代码通过宿主服务调用模型。 | 另一台电脑用自己的 Key 完成并排回答、总结和历史读回；公布实际验证的组合。 |
| P1：日常可靠 | 历史归组、本地时间、错误互评标记、刷新恢复 | 为话题和每次发送分别设置标识；新旧记录保留格式版本；修复空数组误判；显示本地时间；草稿保存与迁移明确提示。 | 连续两轮保留正确上下文，刷新可恢复；旧记录仍能读、导出，迁移不覆盖原件。 |
| P2：更多渠道 | 默认模型通用化、按渠道获取目录、失败后手动配置 | 先删除对特定渠道的默认依赖，再使用宿主的发现能力；模型路由依据明确的 provider/协议/模型配置，不靠模型名猜协议。 | 至少验证官方 DeepSeek、官方智谱和一个中转站；不支持目录查询的接口仍可手动选模型。 |
| P3：比较质量与成本 | 更清楚的总结依据、可选互评、并发控制与用量 | 总结中注明回答是否完整及引用来源；互评另做显式轮次并显示将发送哪些回答；按用户配置排队、取消和重试；用量与价格来源分开记录。 | 一栏失败不拖垮其他栏；截断内容不冒充完整依据；模型一致意见不冒充事实证据。 |

首版暂不实施 P2，只在 README 说明当前限制。自动执行、电脑控制、云同步和独立客户端需要单独明确需求与权限，不能顺手并入安装适配。

## 从哪个文件入手

| 需求 | 主要位置 |
|---|---|
| 渠道、模型清单、后端编排 | `src/index.js`；Wokey 目录发现位于 `src/catalog.js` |
| 模型流式调用、上下文、输出状态 | `src/lanes.js` |
| 浏览器传输、连接中断 | `src/http.js`、`src/client/remote.js` |
| 历史保存与目录解析 | `src/store.js`；轮次状态在 `src/client/panel.js`、`src/client/state.js` |
| 布局与控件 | `src/client/styles.js`、`src/client/lanes-ui.js`、`src/client/components.js` |
| 构建和离线回归 | `build.mjs`、`scripts/test.mjs`、`verify-local.mjs`、`verify-stream-catalog.mjs`、`scripts/verify-storage.mjs` |

## 每次改进都保留这条短流程

**复现问题 → 写清一个验收目标 → 修改源码 → 构建和针对性检查 → 在目标 Harness 中验证 → 更新 README 的支持范围。**

保持模型调用层、数据保存层和界面层分开；不在前端存凭证，不引入个人绝对路径，不为新增渠道复制整套界面。需要扩大模型/客户端支持时核对当前官方文档；没有测试的组合标记为待验证。

已经通过的检查不无理由重复；涉及保存、流式或适配器契约的改动，应补充能覆盖实际失败场景的回归检查。`lib` 是构建产物，`src` 才是修改入口。
